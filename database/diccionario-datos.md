# Diccionario de datos propuesto

Tipos PostgreSQL orientativos. `VARCHAR(n)` requiere que el equipo apruebe límites `n`; `TEXT` puede usarse para `reason` y `address` si no se define un límite. Importes: `NUMERIC(19,2)` sujeto a aprobación. Fechas modeladas como `TIMESTAMP WITHOUT TIME ZONE` para corresponder con `LocalDateTime`.

## Tablas del dominio actual

### `beer_product`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `id` | `VARCHAR(64)` | PK; identificador existente |
| `name` | `VARCHAR(200)` | NOT NULL, no vacío |
| `volume_ml` | `INTEGER` | NOT NULL, `> 0` |
| `units_per_basket` | `INTEGER` | NOT NULL, `> 0` y par |
| `container_type` | `VARCHAR(32)` | NOT NULL; `RETURNABLE_EXCLUSIVE`, `RETURNABLE_SHARED`, `NON_RETURNABLE_CAN` |
| `container_group` | `VARCHAR(100)` | NULL salvo envase compartido, donde se requiere valor no vacío |

### `product_price`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `product_id` | `VARCHAR(64)` | PK parcial, FK a `beer_product` |
| `presentation_code` | `VARCHAR(32)` | PK parcial; `UNIT`, `HALF_BASKET`, `FULL_BASKET` |
| `price` | `NUMERIC(19,2)` | NOT NULL, `> 0`; precio vigente de la presentación |

### `inventory_item`

|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | PK técnica |
| `product_id` | `VARCHAR(64)` | NOT NULL, FK y UNIQUE; un inventario por producto |

### `stock_movement`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | PK técnica |
| `product_id` | `VARCHAR(64)` | NOT NULL, FK a `beer_product` |
| `movement_type` | `VARCHAR(16)` | NOT NULL; `ENTRY` o `EXIT` |

No se incluye columna de actor o venta: no existen en `StockMovement` actual.

### `customer`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `id` | `VARCHAR(64)` | PK; identificador de negocio |
| `name` | `VARCHAR(200)` | NOT NULL, no vacío |
| `phone` | `VARCHAR(50)` | NOT NULL, no vacío |
| `address` | `TEXT` | NOT NULL, no vacío |
| `balance` | `NUMERIC(19,2)` | NOT NULL DEFAULT 0, `>= 0`; deuda agregada del cliente. Se mapea desde `Customer.getBalance()`; el atributo Java `saldo` no necesita cambiar. |

La deuda general se obtiene como `balance - SUM(saldos pendientes de ventas asociadas)`. La asignación de deuda de ventas no se duplica en una columna/tabla.

### `sale_line`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | PK técnica |
| `sale_id` | `VARCHAR(48)` | NOT NULL, FK a `sale` |
| `product_id` | `VARCHAR(64)` | NOT NULL, FK a `beer_product` |

Subtotal derivado: `quantity * unit_price`. Unidades equivalentes derivadas con el código de presentación y capacidad snapshot.

### `sale_payment`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | PK técnica |
| `sale_id` | `VARCHAR(48)` | NOT NULL, FK a `sale` |
| `amount` | `NUMERIC(19,2)` | NOT NULL, `> 0` |
| `timestamp` | `TIMESTAMP WITHOUT TIME ZONE` | NOT NULL |

El pago inicial positivo y cada abono son filas separadas. La suma no debe exceder el total de la venta; validar en operación transaccional.

### `user_account`

| Columna | Tipo | Restricción / significado |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK; permite IDs asignados si el repositorio los requiere |
| `username` | `VARCHAR(100)` | NOT NULL; unicidad funcional sobre `lower(trim(username))` |
| `password_hash` | `VARCHAR(255)` | NOT NULL; hash, nunca contraseña en claro |
| `role` | `VARCHAR(32)` | NOT NULL; `ADMINISTRATOR` o `WORKER` |
| `active` | `BOOLEAN` | NOT NULL DEFAULT TRUE |
| `seller_id` | `VARCHAR(32)` | NULL, FK a `seller` |
| `created_at` | `TIMESTAMP WITHOUT TIME ZONE` | NOT NULL |

La unicidad de `username` debe implementarse como unicidad funcional sobre `lower(trim(username))`, equivalente a la normalización de `InMemoryUserRepository`. La búsqueda debe aplicar la misma normalización. Un índice único funcional evita que ` Ana `, `ana` y `ANA` coexistan.

### Reconstrucción de `sale_line`

Al leer una venta, recuperar `unit_price` y `units_per_basket_snapshot` directamente de cada fila `sale_line`. Nunca reconstruir el precio usando `product_price`, pues representa el precio vigente y podría diferir del cobrado. `SaleLine` requiere una futura fábrica/constructor de rehidratación que acepte ambos valores históricos explícitamente; se conservará el constructor normal de venta para capturar valores actuales.

## Políticas de borrado e índices

Todas las claves foráneas se definen explícitamente con `ON DELETE RESTRICT`, sin cascadas. Así no se puede eliminar una venta con líneas o pagos, ni eliminar catálogo/personas que tengan referencias históricas. Las operaciones fallidas deben usar `ROLLBACK` de la transacción.

Índices sugeridos que no quedan cubiertos por PK/UNIQUE: `sale_line(sale_id)`, `sale_line(product_id)`, `sale_payment(sale_id)`, `sale(seller_id)`, `sale(customer_id, created_at)`, `sale(created_at)`, `stock_movement(product_id, occurred_at)` y `user_account(seller_id)`. El índice compuesto de `sale(customer_id, created_at)` cubre búsquedas por `customer_id`; no hace falta otro índice simple para esa columna. La PK compuesta de `product_price(product_id, presentation_code)` ya cubre búsquedas por `product_id`; no crear índice adicional. `inventory_item(product_id)` ya queda indexado por UNIQUE.

No repetir índices derivados de PK/UNIQUE ni crear un índice simple cuando el mismo prefijo está cubierto por uno compuesto.

## Tablas previstas para módulos futuros

No se proponen todavía tablas para proveedor/compra, recepción, devolución, anulaciones, cuenta corriente/libro de cartera, auditoría, sucursal, lote/caducidad, método de pago o permisos dinámicos. No tienen correspondencia suficiente en las entidades y servicios analizados. Si la política de anulaciones requiere conservar historial, deberá diseñarse antes de habilitar borrado físico de ventas.
